# The GPUI shell for joe Linux

**Use upstream GPUI layer-shell windows for desktop chrome. Give a separate GPUI locker a private compositor role.** The shell, locker, Settings and the eighteen suite apps will use the same pinned `mundane-ui`. Smithay continues to own placement, seat focus, capture authorization and the lock boundary. Step 1 runs as an opt-in GDM session. The Python/GTK shell at `c320d08`, including the three [parity changes and screenshots](parity.md), is the behavioural baseline.

## Processes, surfaces and restart

GDM starts `mundane-session` in the user’s PAM/logind session. Keep its ready handshake, environment publication, user target, sleep inhibitor and portal readiness ordering. The seat compositor creates a socketpair, registers its server end with Smithay as `Role::Shell`, and launches **one `mundane-shell` per session** with the client end and a separate private control descriptor. This extends the existing supervisor. The normal Wayland display remains available to apps launched from Start. Validate inherited descriptors at startup, close them across exec and fail initialization if the trusted channel or expected global is missing. Settings and launched apps connect as ordinary clients. [Session leader](../session/mundane-session) · [Trusted child setup and supervision](../src/shell/services.rs) · [Shell-only layer global](../src/shell/desktop.rs)

One GPUI event loop shares fonts, renderer, app catalogue, device watches and bus ownership across outputs. Create a bottom-anchored top-layer bar with a logical-height exclusive zone on each display. Desktop icons use the bottom layer. Menus use a bounded overlay anchored to the invoking control. Toasts, OSDs and the Alt+Tab preview take no keyboard focus. Reconfigure on scale, mode and output changes. Keep window order, shortcut grabs, workspace membership, restore targets and click consumption in the compositor. The shell renders their snapshots and sends actions tagged with stable window/output IDs. Use change events, resubscribe and obtain a fresh snapshot on restart.

Port the existing shell services to Rust behind the GPUI views. Keep D-Bus handlers, device commands, dave reads and PAM conversations off the render thread. Supervise the shell independently of applications and the locker. On loss revoke capture grants and keyboard-monitor subscriptions, cancel pending prompts, release shell surfaces and reconnect with a new generation and bounded restart backoff. Rebuild tasks and devices from their owners. Retain favourite and delivered-upgrade state in their existing stores across a restart. Keep a single owner for each bus name. During development select the complete reference shell or the GPUI candidate at session start in separate test logins. Advance each candidate feature against the reference before changing the packaged entry point.

### The locker’s private role

1. On lock, Smithay enters the locked state immediately, revokes capture, clears pending input and covers **every** output with its own opaque buffer. Only the locked render path may reach scanout. New outputs start covered. Keyboard, pointer and touch go only to an admitted lock surface, or are withheld until one exists. Keep the VT/session and sleep handling. Report coverage to logind only after all active outputs have presented a protected frame. [Current mask](../src/render.rs) · [Lock lifecycle](../src/shell/lock.rs)
2. Spawn a separate unprivileged `mundane-lock` on demand. Give it a fresh Wayland socket marked with a dedicated GPUI-locker client role and a paired private control socket scoped to this lock attempt. Keep the legacy `ext_session_lock_manager_v1` grant exclusive to the old swaylock client during migration. The GPUI locker uses only the ticket and completion path described here. Send a versioned output snapshot and one-use surface tickets, one per output. The locker opens an ordinary borderless GPUI XDG window per ticket. Carry the ticket as a correlation value in `WindowOptions.app_id`; GPUI sends it during XDG window construction before the initial commit. The compositor admits the window only when **the actual Wayland connection, current lock generation, live output and unused ticket all match**. Consume the ticket once. A matching app ID, PID, title or session UID on another connection confers no authority. [GPUI app ID, window.rs lines 593–600](https://github.com/zed-industries/zed/blob/f4fe0be1/crates/gpui_linux/src/linux/wayland/window.rs#L593-L600) · [Initial commit, lines 877–896](https://github.com/zed-industries/zed/blob/f4fe0be1/crates/gpui_linux/src/linux/wayland/window.rs#L877-L896)
3. Intercept locker toplevels **before** normal mapping, focus, decorations, foreign-toplevel publication or capture enumeration. Keep their XDG protocol role for configure/ack, assign the admitted surface an internal lock role and configure it to the output’s full logical extent. Composite its committed buffer over the mask. Use the mask alone while admission, configure or repaint is pending, including on hotplug, unplug or resize. Discard unknown or stale requests. Neither the shell’s control channel nor the public Wayland socket accepts unlock.
4. The locker authenticates the session user through Linux-PAM and joe’s `mundane-lock` PAM service. Run the conversation as the user on a worker, support echo-off prompts and retries, and clear response buffers after use. Only PAM success can send completion over the live locker channel for the current generation. Wrong password, cancellation, helper error, stale completion and either process channel closing leave the compositor locked. On locker loss, discard its surfaces and tickets, keep the mask and start a fresh attempt. Keep password values out of clipboard, logs, IME surrounding text, AT-SPI text and keyboard-monitor events. Orca must still announce the prompt, error and focus.

### Step 1 in the GPUI preview

GDM’s **mundaneDE (GPUI preview)** entry starts one supervised `mundane-shell`. Each output gets a 44-logical-pixel bottom exclusive zone. The shell subscribes to task changes over the compositor-owned socket and gets a fresh snapshot after a restart. GIO supplies desktop entries, launch, favourites and the StatusNotifier bus service. The bar shows pins in the inherited joe order until the user edits them. A pin launches, restores its window or offers a grouped window menu. Super+Space searches desktop-entry names, IDs, generic names and keywords. Alt+Tab previews the compositor’s selection until Alt is released.

The preview uses the suite’s panel buttons, running and occupied states, badges and tooltips. Favourites use its toggle. Categories use its searchable choice menu, and the tray, grouped windows and basic system actions use its keyed menu choices. Start and the window finder combine the shared text field with per-row actions inside the shared popover. The compositor handles outside-click consumption and returning keyboard focus across Wayland surfaces. Super+S opens the system menu for keyboard access to the tray, Lock and Log Out during this step. Full Quick Settings is gate 2. ### Step 1 measurements

The release build at `0edad6f` ran in an eight-vCPU, 6 GiB KVM guest on an Intel Core Ultra 7 265KF. QEMU used virtio-vga with a 1920×1080 primary scanout and no display window. The enforcing joe beta1 guest used Mesa lavapipe for GPUI Vulkan and llvmpipe for the compositor. The shell ELF build ID was `8d72455cfde517eb438f2652adb572657370c720` and the compositor’s was `fcbefa70d3d309656fbb5d6dd099504aabf0edd1`.

A real seat click on the presented Start button opened a focused search field in **0.562 s** with a fresh user cache. Across 20 subsequent GDM logins, the median was **0.423 s** and p95 was **0.457 s**. The timer starts at the compositor’s shell launch and ends at the first QMP observation of the open menu. The test also checks the field’s focus over AT-SPI. The system font caches shipped in the image were available throughout.

Each configuration settled for 60 seconds before a 60-second CPU sample. PSS and RSS are from the shell’s `smaps_rollup`. The secondary scanout was 1024×768. CPU time has 10 ms resolution, so the single-output sample accumulated less than one tick.

| Configuration | Shell PSS | Change from one output | Shell RSS | CPU, one vCPU |
| --- | ---: | ---: | ---: | ---: |
| One output | 134.2 MiB | +0.0 MiB | 168.1 MiB | 0.000% |
| Two outputs | 137.2 MiB | +3.0 MiB | 171.9 MiB | 0.017% |
| Two outputs with Orca | 137.0 MiB | +2.8 MiB | 172.1 MiB | 0.017% |

Orca itself used 68.3 MiB PSS and 91.3 MiB RSS. On one output, separate PSS measurements were 96.3 MiB for the compositor, 4.0 MiB for PipeWire, 8.7 MiB for WirePlumber, 4.8 MiB for the portal frontend and 19.5 MiB for the GTK portal backend.

With menus closed and a stationary pointer, the compositor logged **zero layer commits and zero DRM redraws** in each 10-second observation either side of a visible clock update. The test repeated this with reduced motion enabled. With transitions enabled, a workspace switch produced intermediate scanout frames. With reduced motion it went directly to the destination.
